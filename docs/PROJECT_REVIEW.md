# EventMind v2 — аудит проекта и план доработок под тему ВКР

> Дата аудита: **19 октября 2026**, ветка `main`.
> Тема, предложенная руководителем: **«Разработка приложения для агрегации и
> рекомендаций ИТ-событий на основе семантического анализа их описания и модели
> пользователя»**.
>
> Документ фиксирует: что проверено и с каким результатом, найденные дефекты,
> степень соответствия теме и конкретный план, что усилить и поменять.

---

## 1. Короткий вывод

- **Инженерно проект сильный**: гексагональная архитектура с автоматической
  проверкой границ слоёв, async по всему стеку, транзакционный outbox,
  отказоустойчивая LLM-цепочка, k8s/Helm, мониторинг. Линтер, строгий mypy и
  155 unit-тестов зелёные.
- **Тема проекту подходит** — все её смысловые блоки в коде присутствуют.
- **Но именно то, что тема ставит в центр, реализовано слабее всего**:
  семантический анализ в стандартном развёртывании выключен, модель
  пользователя минимальна, а офлайн-оценка ничего не доказывает. Инфраструктура
  сейчас заслоняет исследовательскую часть — для магистерской работы баланс
  нужно сместить в сторону метода и эксперимента.
- **LLM используется узко** (только извлечение структуры при загрузке и разбор
  NL-запроса) — её роль в модели пользователя, поиске и оценке качества стоит
  расширить; разбор и идеи — §13.
- **ИИ-агент имеет смысл как диалоговый слой поверх детерминированного ядра**
  (разговорная рекомендательная система), а не как замена рекомендателю;
  веб и бот остаются — §14.
- **Сроки:** ≈ 30–45 рабочих дней на код и эксперименты + 3–5 недель на текст
  ВКР; минимальный путь — ≈ 20–25 дней. Основная работа планируется на
  Windows 11 (обычный PowerShell + Docker Desktop) — §15, запуск —
  `docs/LAUNCH.md`.

## 3. Архитектура — сильные стороны

- Слои `domain → application → infrastructure → interfaces`, контракты
  import-linter: домен не зависит от фреймворков и I/O.
- Порты и адаптеры: LLM, эмбеддинги, каналы доставки, источники ingestion
  подменяемы без правок бизнес-логики.
- Надёжность: транзакционный outbox, идемпотентный ingestion с ретраями и DLQ,
  circuit-breaker и per-provider cooldown в LLM-цепочке.
- Мультиканальная доставка (email / Telegram / in-app) с тихими часами.
- Двухстадийный рекомендер: kNN-кандидаты на pgvector (HNSW) → гибридное
  ранжирование → MMR → анти-флуд серий.
- Эксплуатация: Helm (HPA, PDB, миграции как hook), Prometheus-алерты,
  Grafana, k6-смоук, CI.

## 4. Соответствие теме — разбор по смысловым блокам

| Блок темы | Что есть сейчас | Чего не хватает |
|---|---|---|
| **Агрегация** | 3 источника (habr, rss, kudago), пайплайн source → raw_events → events, идемпотентность | Нет периодического запуска (только ручной вызов API); нет семантической дедупликации между источниками; в v1 было 6 источников |
| **Семантический анализ описаний** | LLM извлекает структуру (темы, формат, тип, дата, стек, уровень); MiniLM-384 строит эмбеддинги | В Docker/Helm-образе эмбеддинги **не считаются** (см. D1); NL-поиск — `ILIKE`, а не векторный; модели эмбеддингов не сравнивались; качество LLM-извлечения не измерено |
| **Модель пользователя** | Beta-распределение по темам + эмбеддинг = среднее лайкнутых событий + город/формат. ✅ *После P0 №3–5:* текстовый профиль «о себе» с LLM-выжимкой, эмбеддинг по Rocchio (профиль + позитивы − дизлайки), объявленные интересы/анти-интересы в скоринге, D2 исправлен | ~~Нет текстового профиля / интересов / целей / уровня; холодный старт без персонализации; дизлайки не влияют на эмбеддинг; баг затухания (D2)~~ Осталось: онбординг в боте (B2), вклад в eval (№6) |
| **Рекомендации** | Гибрид rule + cosine + bayesian + quality + hype + freshness, MMR | Веса «эмпирические из v1», не обоснованы; уже оценённые события возвращаются в выдачу (D3); offline-eval не доказателен (§6) |
| **Приложение (интерфейсы)** | Веб на Next.js, Telegram-бот, email-дайджесты | Бот не самостоятельный интерфейс (§7) |

Итог: тема **корректна и соответствует проекту**, но обязывает усилить
семантическую часть и модель пользователя. Новизна относительно прошлой
курсовой («…на основе модели пользователя») — именно «семантический анализ»,
поэтому он должен стать главным содержанием ВКР.

## 5. Найденные дефекты

### D1. Семантика выключена в стандартном развёртывании — критично для темы
- `backend/Dockerfile` не ставит extra `ml` (torch + sentence-transformers).
  В комментарии — «эмбеддинги грузятся в отдельном ml-образе», но такого образа
  нет. Helm использует тот же образ → в проде то же самое.
- `NormalizeRawEvents._safe_embed` (`application/ingestion/use_cases.py`) молча
  возвращает `None`. Следствие: у событий нет векторов → `cosine` всегда 0 →
  у пользователей не появляется эмбеддинг → kNN-стадия не используется → MMR
  работает без векторов.
- Обещанный «backfill в M4» не реализован: события без эмбеддинга так и
  остаются без него.

> **Статус (P0 №1, №2):** образ теперь ставит extra `ml` (torch CPU + MiniLM),
> модель кэшируется в volume `hf-cache`. Backfill сделан (P0 №2):
> `BackfillEventEmbeddings` + пересчёт эмбеддингов лайкнувших пользователей —
> cron раз в час и `POST /api/v1/ingestion/backfill-embeddings`.

### D2. Баг temporal decay: дизлайк повышает интерес
`infrastructure/db/recommendation.py::apply_feedback_to_stats`. Затухание
применяется только при чтении (`apply_decay`), а при записи берётся **сырое,
незатухшее** α/β, после чего `updated_at` сбрасывается на «сейчас».
Воспроизведено на доменных функциях:

```
10 лайков год назад, чтение сейчас:    α ≈ 5.8, β = 1
+ 1 дизлайк сегодня:                   α = 31,  β = 3   ← интерес «воскрес»
```

Исправление: перед прибавлением дельты материализовать затухание
(`alpha, beta = apply_decay(stat.alpha, stat.beta, stat.updated_at, now=…)`).
Добавить регрессионный тест.

> **Статус (P0 №3): ✅ исправлено.** Доменная функция `apply_feedback`
> (`domain/recommender/bayesian.py`) сначала материализует decay на момент
> `now`, затем прибавляет дельту; репозиторий выставляет `updated_at = now`
> по часам приложения. `RecordInteraction` получает `Clock` и γ из
> `ScoringWeights`. Регрессионные unit-тесты — `test_recommender_math.py`.

### D3. «Скрыть» / оценённые события возвращаются в ленту
`PgvectorCandidateGenerator` и `GetRecommendations` не исключают события, с
которыми пользователь уже взаимодействовал. После инвалидации кэша
скрытое (dislike), лайкнутое и сохранённое снова попадает в выдачу — и в вебе,
и в боте. Нужно исключать `interactions` пользователя на стадии кандидатов.

> **Статус (P0 №3): ✅ исправлено.** `CandidateGenerator.generate(...,
> exclude_interacted_by=user_id)` — в обеих ветках (kNN и cold-start) события с
> like / dislike / save пользователя исключаются подзапросом; `view` не
> исключает. Интеграционные тесты — `test_recommendations_api.py` (⏳ локально
> не прогнаны: на macOS testcontainers/Ryuk не стартует под Docker Desktop —
> прогнать в CI или на Windows).

### D4. Мелкие
- ~~Нет cron для ingestion/нормализации — в worker только cron дайджестов.~~
  ✅ Исправлено в P0 №2.
- `PgvectorCandidateGenerator.generate(city=…)` — параметр не используется.
- `freshness_score` даёт событиям без даты 0.5 — столько же, сколько событию
  через месяц; статьи без даты получают незаслуженный буст.
- Веса `skill_gap / bandit / gnn` объявлены в `ScoringWeights`, но скореров нет.
- `dedup_threshold = 0.92` объявлен, но нигде не используется.
- Компоненты гибрида в разных шкалах (rule не ограничен сверху, cosine ×10,
  quality ×0.5) — сумма плохо интерпретируема, веса не калиброваны.

## 6. Офлайн-оценка — почему сейчас она ничего не доказывает

Текущий результат `python -m eval.run` (синтетика, 40 пользователей × 160 событий):

```
variant        nDCG@10   MAP    R@10
rule_only       0.502   0.346   1.00
content_only    0.298   0.233   0.60
bayesian_only   0.131   0.124   0.25
full            0.487   0.330   1.00
full_no_mmr     0.513   0.360   1.00
```

- Гибрид **не лучше** одних правил, MMR ухудшает метрики.
- Датасет вырожден: у каждого события ровно одна тема; цель выбирается
  случайно среди 6–7 равнозначных событий той же темы → R@10 = 1.0 у правил
  тривиален, остальное — случайность выбора цели.
- **Утечка**: эмбеддинг пользователя строится из *истинных* интересов, а не
  так, как это делает система (среднее по лайкам).
- Нет реальных текстов и реальной модели эмбеддингов — «семантический
  анализ» не оценивается вовсе.
- Нет базовых линий (random, popularity, TF-IDF/BM25).

Для отчёта это нельзя подавать как подтверждение качества (§9 — что делать).

Дополнительно: текст прошлого отчёта описывает LinUCB, LightGCN, mem0-память —
в v2 их нет. Отчёт и код нужно синхронизировать.

## 7. Telegram-бот — статус

**Реализован** (`backend/src/eventmind/interfaces/bot`, aiogram 3, long-polling,
compose-профиль `bot`) как *вторичный* клиент поверх API:

- `/start <token>` — привязка аккаунта по deep-link из веб-кабинета;
- `/feed` — лента рекомендаций, под карточкой 👍 / ⭐ / 👎 / 📖;
- `/search <фраза>` и свободный текст — NL-поиск;
- Telegram как канал доставки дайджестов (M5).

**Самостоятельным интерфейсом бот не является. ✅ Зафиксировано: реализовать
обязательно (задачи B1–B5 в §8, приоритет P0):**

- **B1. Без аккаунта в вебе бот бесполезен — регистрации прямо в боте нет.**
  Без привязки API отвечает 409 `not_linked`, лента и оценки недоступны.
- **B2. Нет онбординга интересов, настроек и списка сохранённого.**
  Пользователь не может из бота рассказать о себе, поменять город / формат /
  дайджест и посмотреть, что сохранил.
- **B3. «📖 Подробнее» просто показывает ту же карточку ещё раз.**
  Нет ни развёрнутого описания, ни объяснения «почему рекомендовано».
- **B4. Лента приходит сразу 20 сообщениями.** `/feed` отправляет всю выдачу
  (`result_limit = 20`) подряд — это спам в чате.
- **B5. Под результатами поиска нет кнопок оценки.** Только ссылка на
  источник: из поиска нельзя лайкнуть / сохранить / скрыть, сигнал для модели
  пользователя теряется.

**Желательно (P1):**

- Меню команд (`set_my_commands`), кнопка «🔍 Похожие» на карточке.
- Запуск бота в стандартном `make up` (сейчас только через профиль `bot`).
- Связано с D3: «👎 Скрыть» сейчас не скрывает — чинится в P0 №3.

**Где лежит код бота — структурная оценка.** Бот находится в
`backend/src/eventmind/interfaces/bot/`. По гексагональной схеме это слой
входящих (driving) адаптеров, так что размещение допустимо. Из backend бот
импортирует только `eventmind.config` и `eventmind.infrastructure.logging`, а
с системой общается по HTTP через `BotApiClient`. Это даёт один образ, общий
конфиг, единые mypy/ruff/CI.

Нюанс: по сути бот — **внешний клиент API**, такой же, как `web/`, а не
адаптер, вызывающий use-case'ы напрямую. Слой `interfaces` по контракту
import-linter имеет право импортировать всё, поэтому статус «только через API»
ничем не защищён. Рекомендация: оставить бота на месте, но добавить
forbidden-контракт `eventmind.interfaces.bot` ↛ `application / domain /
infrastructure.db` (кроме config и logging). Выносить бота в отдельный
top-level пакет (`bot/` рядом с `web/`) имеет смысл, только если его
собираются версионировать и деплоить независимо от backend.

## 9. Экспериментальная часть для ВКР — предлагаемый дизайн

**Гипотезы:**
- H1. Семантические представления описаний повышают качество рекомендаций
  относительно правил по темам и лексических методов (TF-IDF/BM25).
- H2. Текстовый профиль пользователя улучшает холодный старт.
- H3. Гибрид (семантика + байесовская адаптация по фидбэку) лучше каждой
  компоненты по отдельности.
- H4. Эмбеддинг канонического LLM-пересказа описания точнее эмбеддинга
  сырого текста со страницы источника.

**Данные:** реальный корпус событий из источников (≥ 500–1000), плюс
разметка релевантности: персоны-профили × события (вручную или с LLM-судьёй
и выборочной ручной проверкой), либо реальные взаимодействия тестовой группы.

**Базовые линии:** random, popularity/quality, rule-only, TF-IDF, BM25.

**Варианты:** MiniLM / e5 / bge-m3; сырой текст / LLM-пересказ;
профиль-только / история-только / смесь;
гибрид с весами по умолчанию и с обученными весами; ±MMR.

**Метрики:** Recall@k, nDCG@k, MAP, coverage, intra-list diversity,
novelty; для холодного старта — метрики на первых N рекомендациях; время
ответа (p50/p95).

**Протокол:** временной сплит (train — прошлое, test — будущее) или
leave-one-out на реальных взаимодействиях; фиксированный seed; статистическая
значимость (bootstrap / парный тест Уилкоксона).

## 13. Роль LLM в проекте

### 13.1. Что LLM делает сейчас

LLM вызывается ровно в двух местах, оба — вне пути выдачи рекомендаций:

1. **Нормализация при загрузке** (`application/ingestion/normalizer.py`): из
   сырого описания извлекается структура — «это IT-событие?», темы, формат,
   город, тип, дата, стек, уровень, плюс `quality_score` / `hype_score` (1–10).
2. **NL-поиск** (`application/search/use_cases.py`): фраза пользователя →
   фильтры `SearchFilters`. Кэша запросов в v2 нет (в v1 был LRU) — каждый
   поиск = вызов LLM.

Итого сейчас LLM — **извлекатель структуры из текста**; дальше работают SQL,
правила и байесовская модель.

### 13.2. Эмбеддинги — не через DeepSeek

- **Практически:** в официальном прайсе DeepSeek (проверено 19.10.2026,
  api-docs.deepseek.com/quick_start/pricing) только чат-модели
  `deepseek-flash` и `deepseek-v4-pro`; модели и эндпоинта эмбеддингов нет.
- **Принципиально:** эмбеддинги для поиска и рекомендаций строят
  энкодеры, обученные контрастивно («похожие тексты рядом, непохожие далеко»).
  Чат-LLM для этого не предназначена: дороже и хуже маленького энкодера.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Локальные** (сейчас MiniLM-384; сильнее — `multilingual-e5`, `bge-m3`, русскоязычные `USER-bge-m3`, `sbert_large_nlu_ru`) | Бесплатно, воспроизводимо, данные не уходят наружу; в Docker — через ONNX без torch | Место и CPU, первая загрузка модели |
| **API** (OpenAI, Gemini embeddings, YandexGPT / GigaChat embeddings) | Ничего не хранить у себя | Платно, зависимость от сети, хуже воспроизводимость, данные пользователей уходят наружу |

Для ВКР — **локальные**; сравнение 3–4 энкодеров на реальных данных — готовый
эксперимент (P1 №9).

### 13.3. Нужна ли LLM вообще

**Нужна, но в правильной роли.** Без неё — отдельный парсер под каждый
источник, регулярки для дат и классификатор тем: возможно, но хрупко и
заново на каждом источнике. LLM даёт универсальное понимание разнородных
описаний — это и есть «семантический анализ описаний» из темы.

Принцип: **LLM понимает и обогащает текст → эмбеддинги сопоставляют →
байесовская модель учится на поведении.** LLM вызывается один раз на событие
или на изменение профиля, результат кэшируется и хранится. В горячий путь
выдачи рекомендаций её не ставить: медленно, дорого, невоспроизводимо.

Что сейчас сомнительно (→ P1 №14):
- **`quality_score` / `hype_score`** — непроверенные субъективные оценки LLM,
  которые входят в ранжирование с весом. Проверить на разметке или убрать.
- **Нет защиты от prompt injection** (в v1 был `prompt_safety`), а в промпт
  идут тексты со сторонних сайтов и запросы пользователей.
- **Нет провенанса:** температура 0.3 для извлечения, модель и версия промпта
  не сохраняются. Для научной работы — температура 0 и `llm_model` +
  `prompt_version` при событии.

### 13.4. Как использовать LLM эффективнее

**Анализ описаний событий**
- **Каноническое описание для эмбеддинга:** LLM переписывает шумный HTML в
  единый формат (о чём, для кого, что получите, стек, уровень); эмбеддинг
  строится по нему. Эксперимент «сырой текст vs пересказ» — проверка H4.
- **Более богатая структура события:** результаты обучения, требования к
  знаниям, спикеры и компании, язык, цена, дедлайн регистрации; навыки —
  к единому справочнику, а не свободными строками.
- **LLM-арбитр дедупликации:** пары с близостью 0.85–0.92 спорные — LLM
  решает «одно ли это событие». Дешевле, чем гонять LLM по всем парам.

**Модель пользователя (главное по теме)**
- **Профиль из свободного текста:** «бэкендер на Go, 3 года, хочу в ML,
  офлайн только в Перми» → роль, уровень, стек, цели, интересы,
  анти-интересы, город, формат → эмбеддинг профиля. Закрывает холодный старт
  и B2 для бота (P0 №4).
- **Интерпретируемый портрет пользователя:** раз в N взаимодействий LLM
  пишет «как система вас видит» по лайкам и дизлайкам; пользователь правит
  текст. Кандидат на научную новизну работы (P1 №17).
- **Цели → недостающие навыки:** из «хочу стать ML-инженером» LLM выводит
  нужные навыки, рекомендатель ищет события, закрывающие пробелы (оживляет
  объявленный, но не реализованный `skill_gap`; P1 №18).

**Поиск и ранжирование**
- **HyDE:** LLM сочиняет описание «идеального события» под запрос → его
  эмбеддинг → kNN. Поиск становится семантическим, а не `ILIKE` (P1 №16).
- **LLM-переранжирование top-20** — в офлайн-эксперименте как верхняя граница
  качества; затем можно дистиллировать в лёгкую модель.
- **Объяснения «почему рекомендовано»** (B3, P1 №11) — по реальному вкладу
  компонентов, а не выдуманные.
- **Диалоговое уточнение в боте:** «то же, но онлайн и для джунов».

**Оценка качества (закрывает главную дыру — §6)**
- **LLM-судья для разметки релевантности** «персона × событие» + ручная
  проверка подвыборки с κ Коэна (P0 №6).
- **Синтетические персоны и симуляция пользователей** — полезно, но есть
  риск круговой логики, если один и тот же LLM и генерирует, и оценивает;
  оговорить в работе.
- **Золотая выборка для проверки самого извлечения** (P1 №12).

**Доставка**
- Персональное вступление к дайджесту: «на этой неделе для вас три события
  по Go и одно по ML».

### 13.5. Риски

- **Стоимость и лимиты:** `deepseek-flash` дешёвый, в непиковые часы — вдвое
  дешевле; удобно для пакетной нормализации.
- **Данные пользователей у внешнего провайдера** (особенно «о себе»): нужно
  согласие пользователя, по 152-ФЗ — вопрос трансграничной передачи.
  Компромисс: профиль обрабатывает LLM, эмбеддинги строятся локально.
- **Невоспроизводимость экспериментов:** температура 0, фиксированная
  версия модели, кэш ответов.

### 13.6. Что брать в ВКР в первую очередь

1. Профиль пользователя из свободного текста через LLM + локальный эмбеддинг.
2. Каноническое LLM-описание события и эксперимент «сырой текст vs пересказ».
3. Сравнение 3–4 локальных энкодеров.
4. LLM-судья с ручной проверкой части разметки — для честной офлайн-оценки.
5. Объяснения рекомендаций и HyDE-поиск.

## 14. ИИ-агент

### 14.1. Нужен ли агент

**Возможно и полезно — но поверх рекомендателя, а не вместо него.** Тема
хорошо ложится на известное направление исследований — **разговорные
рекомендательные системы** (conversational recommender systems, CRS): LLM-агент
выясняет предпочтения в диалоге и обновляет модель пользователя, а подбор
делает измеримое ядро.

- **Конвейер** (как сейчас): шаги заданы заранее, LLM вызывается в
  фиксированных местах.
- **Агент**: LLM в цикле сама выбирает инструмент, смотрит на результат и
  решает, что дальше — уточнить, поискать иначе, записать предпочтение.

Агент оправдан там, где путь к результату заранее неизвестен и зависит от
диалога. Где путь известен — он только добавляет цену, задержку и
непредсказуемость.

### 14.2. Где агент полезен

1. **Диалоговый помощник поверх рекомендаций** — главный сценарий:
   ```
   — Подбери что-нибудь по Go на выходные в Перми
     → search(topics=[go], city=perm, dates=weekend) → пусто
     → «В Перми ничего нет. Онлайн подойдёт?»
   — Да, но только не для новичков
     → recommend(format=online, level≥middle) → 3 карточки
   — Почему второе?
     → explain(event_id) → «совпадает с вашим стеком Go и интересом к highload»
   ```
2. **Агент как редактор модели пользователя** — самая сильная связка с темой:
   «фронтенд больше не интересен» → `update_profile(anti_interests += frontend)`;
   «хочу перейти в ML» → `set_goal(...)` → недостающие навыки → события под
   них. Модель пользователя строится и уточняется в разговоре, а не только
   анкетой.
3. **Агент-сборщик для агрегации** (опционально): по ссылке на произвольный
   сайт сам разбирается со страницами и пагинацией и извлекает события.
   Закрывает слабость «три источника с ручными парсерами»; точность измерима.
4. **Проактивный режим** (дополнительно): раз в неделю сам проверяет новые
   события под цели пользователя и пишет личное сообщение с объяснением.

### 14.3. Где агент не нужен

- **В самом ранжировании.** Ядро «эмбеддинги + модель пользователя + гибрид»
  остаётся детерминированным и измеримым — на нём держится научная часть.
- **В загрузке и нормализации по расписанию** — это пакетная обработка, там
  нужен конвейер.
- **Агент вместо всего приложения.** Чат без сильного ядра под ним — обёртка
  над поиском, защищать будет нечего.

**Урок из v1.** Copilot v1 (LangGraph: супервизор + 5 специалистов) на демо
признали неудобным и скрыли. Типичные причины: слишком много агентов для
задачи одного агента с инструментами; непонятная ценность («поговорить с
ботом» вместо «найди / объясни / запомни»); нет оценки. Вывод: **один агент,
6–8 инструментов, конкретные сценарии, измеримый результат.**

### 14.4. Веб и бот остаются — что меняется

Ничего не заменяется полностью: агент добавляется как ещё один способ
взаимодействия. Кнопки и экраны — для частых и понятных действий (лайк,
сохранить, листать ленту), это быстрее чата. Агент — для того, что неудобно
делать формой: сложные запросы, уточнения, разговор об интересах.

**Веб**

| Функция | Что с ней будет |
|---|---|
| Лента (like · save · hide) | Остаётся как есть |
| NL-поиск | Остаётся: быстрый поиск без лишних вызовов LLM |
| Карточка события, «Подробнее» | Остаётся; объяснение «почему» — тот же use-case, что вызывает агент |
| Настройки, профиль | Остаются; агент меняет те же поля, изменения видны и тут, и там |
| **Новое: панель помощника** | Чат сбоку или отдельной страницей |
| Онбординг | Анкета — запасной вариант; по умолчанию диалог из 2–3 реплик |

**Telegram-бот**

| Функция | Что с ней будет |
|---|---|
| `/feed`, `/saved`, `/settings`, кнопки 👍 ⭐ 👎 📖 | Остаются как быстрые действия |
| `/search <фраза>` | Остаётся как прямой поиск без агента |
| **Свободный текст** | **Единственная настоящая замена:** сейчас уходит в NL-поиск, будет уходить агенту. Агент сам решает — поиск, правка профиля, вопрос «почему» или уточнение |
| Онбординг (B2) | Естественно делается диалогом с агентом |

Бот выигрывает от агента больше всего — он и так разговорный интерфейс.

### 14.5. Архитектура

```
 Telegram-бот / веб-чат
          │
   AgentTurn (use-case, application)
   LLM с tool calling (DeepSeek поддерживает) · лимит шагов · лимит стоимости
          │ инструменты = существующие use-case'ы
   ┌──────┼─────────┬───────────┬──────────────┬────────────┐
 search  recommend  get_event  record_feedback  update_profile  explain
          │
   Детерминированное ядро: эмбеддинги · модель пользователя · гибрид
```

- Агент — ещё один входящий адаптер гексагона: логику не дублирует, вызывает
  те же use-case'ы, что веб и бот. Изменения через агента сразу видны в ленте и
  настройках, и наоборот.
- **Память агента = модель пользователя** (структурный профиль + читаемый
  портрет, который пользователь может править, §13.4). Отдельная «память
  чата» не нужна — только история текущего диалога.
- **Ограничения:** белый список инструментов; подтверждение перед изменением
  профиля; не больше N шагов на ход и лимит токенов; журнал вызовов
  инструментов (для отладки и для главы с оценкой); защита от prompt injection.
- **Деградация:** если LLM недоступна, отключается только чат — лента,
  поиск, кнопки и дайджесты работают, ядро от агента не зависит.

### 14.6. Как оценивать агента

Без оценки агент на защите — демо-фокус.

- **Симуляция пользователей:** LLM играет персону со скрытыми предпочтениями
  и ведёт диалог с агентом. Метрики: через сколько реплик в выдаче
  появляется целевое событие; Recall@k после N реплик.
- **Сравнение онбординга:** качество холодного старта после 3 реплик диалога
  против анкеты — прямая проверка H2.
- **Точность вызовов инструментов** на наборе типовых запросов.
- **Небольшое пользовательское исследование** (5–10 человек, оценка удобства).
- Риск круговой логики (LLM-симулятор оценивает LLM-агента) — оговорить и
  подкрепить ручной проверкой.

### 14.7. Агент и тема

**Тему менять не нужно.** Агент — реализация интерфейса и способ строить
модель пользователя; он прямо работает на «модель пользователя» из названия.
Добавлять «с использованием LLM-агента» в название не стоит: это поднимает
ожидания, и за агента придётся отчитываться отдельно. В тексте ВКР —
«диалоговый агент для выявления предпочтений и уточнения модели пользователя».

**Порядок работ:** ядро (P0) → агент A1–A5 в боте, затем в вебе → оценка A6 →
агент-сборщик — если останется время.

## 15. Сроки и окружение разработки

### 15.1. Оценка сроков

Оценка в **рабочих днях** (полный день сфокусированной работы). Код в основном
пишет Claude Code; ставить задачи, проверять и тестировать руками — на
разработчике. Без помощника цифры по коду — примерно ×2–3.

| Этап | Дней | Что съедает больше всего времени |
|---|---|---|
| **S1 — инструкция и промпт запуска** | 1–2 | Проверка «с нуля» на чистой Windows 11 |
| **P0 — ядро** (эмбеддинги в образе, backfill + cron, D2/D3, текстовая модель пользователя, Rocchio) | 5–8 | Сборка образа с ML-зависимостями; на Windows 11 заметно проще, чем на macOS 12 (§15.2) |
| **P0 — честная оценка** (корпус, разметка, базовые линии, абляции) | 5–8 | **Данные, а не код:** набрать 500–1000 реальных событий и вручную проверить 200–300 пар «персона × событие» после LLM-судьи |
| **P0 — бот B1–B5** | 4–6 | B1: сейчас `users.email` обязательный и уникальный — регистрация через Telegram без email требует миграции и правок авторизации |
| **P1 — ключевое** (энкодеры, H4, гибридный поиск, LLM-гигиена, объяснения, калибровка весов) | 6–10 | Прогоны экспериментов на CPU (крупные энкодеры вроде bge-m3) |
| **Агент A1–A6** | 9–13 | Оценка A6 (симуляция пользователей) и отладка поведения агента |
| **Итого код и эксперименты** | **≈ 30–45** | |
| Текст ВКР | 3–5 недель | Главы, таблицы, рисунки, вычитка |

**В календаре:**

| Режим | Код и эксперименты | Вместе с текстом ВКР |
|---|---|---|
| Полный день (~5 дней в неделю) | ~1.5–2 месяца | ~2.5–3 месяца |
| Параллельно с учёбой / работой (~2 дня в неделю) | ~3.5–5 месяцев | ~5–6 месяцев |

**Минимальный путь** (тема раскрыта, есть что защищать) — **≈ 20–25 рабочих
дней** кода и экспериментов:
1. S1 + P0 — ядро и честная оценка (обязательно);
2. бот: B1, B2, B4, B5 (B3 — упрощённо);
3. P1: сравнение энкодеров, каноническое описание (H4), LLM-гигиена;
4. агент: A1–A4 в боте + упрощённая оценка A6, без веб-чата A5.

**От чего зависят сроки:**
- Код Claude Code пишет быстро; медленные части — данные и разметка, ожидание
  прогонов, ручная проверка и текст ВКР.
- Источники: если habr + rss + kudago не дадут нужный объём будущих событий —
  добавлять источники (Timepad и др.) или копить данные несколько недель через
  ingestion по расписанию. Включить cron ingestion (P0 №2) нужно как можно
  раньше, чтобы корпус копился параллельно с остальной работой.
- Если руководитель сочтёт агента необязательным — минус 9–13 дней.

### 15.2. Окружение: macOS 12 (текущее) и Windows 11 (основное)

**macOS 12 Intel — ограничения, выявленные в этой сессии:**
- Docker Desktop — максимум 4.30 (новее требует macOS 13+); Colima не
  запускается (не собирается qemu).
- Многие Python-пакеты не имеют готовых колёс под macOS 12 x86_64 и
  собираются из исходников (например, `cryptography` 49 требует Rust);
  `uv sync --frozen` из-за этого зависает или падает.
- Подходит для правки кода, unit-тестов и документов; для полного стека с
  ML — неудобна.

**Windows 11 — основная машина для запуска и экспериментов.** Решение:
**обычная Windows + Docker Desktop, без WSL как рабочей среды.**
- Docker Desktop использует WSL2 только внутри себя как движок (ставится
  установщиком автоматически); открывать WSL и работать в нём не нужно.
- **Режим A (всё в контейнерах):** на хосте нужны только Git и Docker Desktop;
  команды Makefile выполняются напрямую через `docker compose` в PowerShell
  (`make` на Windows нет).
- **Режим B (backend на хосте):** `uv` и Python 3.12 работают на Windows
  нативно; у torch есть колесо `win_amd64` (в отличие от macOS 12 x86_64) —
  эмбеддинги до P0 №1 считаются этим путём.
- Подводные камни Windows и их решения:
  - **окончания строк:** в репозиторий добавлен `.gitattributes`
    (`* text=auto eol=lf`) — Git не превратит файлы в `CRLF`; `.env` сохранять
    в `LF` / UTF-8;
  - **настройки читают `.env` из текущей папки** — при запуске backend из
    `backend/` передавать `uv run --env-file ../.env`; адреса Postgres / Redis /
    SMTP / API в `.env` рассчитаны на Docker-сеть, для хоста переопределяются
    переменными оболочки (они имеют приоритет над `--env-file`);
  - `curl` в PowerShell — псевдоним `Invoke-WebRequest`: использовать
    `curl.exe` или `Invoke-RestMethod`;
  - кэш HuggingFace без Developer Mode работает без симлинков (только
    предупреждение; `HF_HUB_DISABLE_SYMLINKS_WARNING=1`);
  - Python строго 3.12 (`requires-python = ">=3.12,<3.13"`).

Всё это расписано в [`docs/LAUNCH.md`](LAUNCH.md).
